# アーキテクチャ

## 全体像

```
                    ┌──────────────── ダッシュボード (public/) ────────────────┐
                    │ 承認待ち / プロジェクト / タスク / レビュー履歴 / 成果物 / ログ │
                    └───────────────▲──────────────────────┬──────────────────┘
                                SSE │                      │ REST(承認・作成)
                    ┌───────────────┴──────────────────────▼──────────────────┐
                    │                  HTTPサーバー (src/server)               │
                    └───────────────▲──────────────────────┬──────────────────┘
                                    │                      │
  ┌─────────────┐   change/event    │   ┌──────────────────▼──────────────────┐
  │ Store       │◀──────────────────┴───│ Orchestrator (src/core)             │
  │ state.json  │                       │ 計画→承認→実行→レビュー→修正→承認   │
  │ events.jsonl│◀──────────────────────│ Approvals(人間の承認待ち)           │
  └─────────────┘                       └──────────────────┬──────────────────┘
                                                           │ AgentProvider
                         ┌─────────────────────────────────┼─────────────────────┐
                         ▼                                 ▼                     ▼
                ClaudeCodeProvider                 CommandProvider          MockProvider
          (Claude Agent SDK, ツール承認)         (Codex CLI など)        (テスト・デモ)
```

## 処理の流れ

1. **計画**: 統括ディレクター(`director`)がプロジェクトの目的をタスクに分解する。
   各タスクには担当役割・依存関係・レビュアー・承認の要否が付く。計画は構造化出力(JSONスキーマ)で受け取り、
   役割の存在・依存先・循環を検証する。不備があれば理由を添えて最大2回作り直させる。
2. **計画の承認**: 計画は「意思決定」として人間の承認を待つ。却下するとコメントを踏まえて再計画する。
3. **実行**: 依存関係が満たされたタスクから、最大 `MAX_PARALLEL` 件を並行に実行する。
   担当AIには、使命・判断基準・前工程の成果を渡し、成果物はワークスペースにファイルとして保存させる。
   出力には要約と**判断理由**を必須項目として含める。
4. **相互レビュー**: 担当以外の役割(既定は品質検証)が、担当の判断基準と自分の判断基準で採点する。
   不合格の場合は、問題・**根本原因**・修正案を出させる。
5. **修正と再検証**: 不合格なら、前回の成果とレビュー内容を渡して修正させ、再びレビューする。
   `MAX_ATTEMPTS` 回で合格しなければ、人間に判断を仰ぐ(承認=現状で完了、却下=失敗)。
6. **公開・費用の承認**: 計画で承認制にしたタスクは、レビュー合格後に人間の承認を待つ。却下するとコメントを踏まえて修正する。

状態はすべて Store にあり、`Orchestrator.tick()` が現在の状態から次の処理を決める。
再起動時は `resume()` が中断した実行をやり直し、待ち手のいなくなったツール承認を無効にする。

## 人間の承認(ヒューマン・イン・ザ・ループ)

| 承認の種類 | 発生する場面 | 承認 | 却下 |
|---|---|---|---|
| `plan` | 計画ができたとき | 実行開始 | コメントを踏まえて再計画 |
| `task_gate` | 公開・費用発生を伴うタスクがレビューに合格したとき | 完了 | コメントを踏まえて修正 |
| `quality_escalation` | 修正上限に達しても不合格のとき | 現状で完了 | タスク失敗 |
| `budget` | プロジェクトの使用額が予算に達したとき | 予算を追加して続行 | 一時停止のまま |
| `business_budget` | 事業の今月の費用が月予算に達したとき | そのプロジェクトは今月に限り続行 | 一時停止のまま |
| `tool` | エージェントが危険な操作をしようとしたとき | 操作を実行 | 操作せずに続行させる |

`tool` 承認は Claude Agent SDK の `canUseTool` で実装している。`src/policy/risk.ts` の規則で、
`git push`・デプロイ・パッケージ公開・外部へのデータ送信・クラウド/決済の操作・外部連携(MCP)ツールなどを検出し、
人間が決めるまでエージェントを待たせる。ワークスペース外のファイルへのアクセスは常に拒否する。

この規則は文字列のパターンによる判定であり、抜け道をすべて塞げるものではない。
本番運用では、エージェントを動かす環境自体(コンテナ、ネットワーク制限、認証情報を渡さない)でも外部への影響を制限すること。

## 事業(複数チームの管理)

プロジェクトは「事業」にまとめられる(事業に属さないプロジェクトも作れる)。事業は次を持つ。

- 既定のチーム: その事業で新しいプロジェクトを作るときに引き継ぐ役割の組み合わせ
- 月予算(任意): 事業に属する全プロジェクトの今月の費用の上限。達するとプロジェクトを止めて承認を求める
- KPI(任意): 売上・会員数などの成果指標。目標と現在値は人間が入力し、全体画面に達成率を表示する

事業はアーカイブ(一覧から隠し、新しいプロジェクトを作れなくする。進行中のプロジェクトは続く)と、
プロジェクトが1つもない場合に限り削除ができる。プロジェクトは別の事業へ移せて、費用の集計も一緒に移る。

費用はプロジェクトごとに月別(`spendByMonth`、サーバーのローカル時刻の 'YYYY-MM')に記録し、事業の今月の費用はその合計で求める。
ダッシュボードの全体画面では、事業ごとに進行状況・承認待ち・今月の費用を一覧できる。

## 役割の定義

役割は state に保存され、管理画面の「役割」から編集・追加できる。`src/roles/catalog.ts` は標準の役割(初回起動時の初期値)で、
標準の役割はいつでも初期値に戻せる。追加した役割は、どの事業・プロジェクトのチームにも入っていなければ削除できる。
変更は次の作業から反映され、実行中の作業には影響しない。各役割は次を持つ。

- `mission`: 使命(何をする役割か)
- `criteria`: 判断基準。実行時は自己チェック、レビュー時は採点基準として使う
- `provider`: 担当するAIサービス
- `tools`: 使ってよいツール(Claude Code の `tools` オプションで制限される)。画面から選べるのは `TOOL_CHOICES` のものだけ
- `model` / `effort`: 使うモデルと思考レベル(省略時は既定)

`director`(計画)と `qa_reviewer`(品質検証)は全プロジェクトに必ず入る。

## 拡張: 他のAIサービス

`AgentProvider` を実装して `ProviderRegistry` に登録すれば、役割の担当にできる。
プロバイダは「プロンプトとJSONスキーマを受け取り、スキーマに沿ったJSONと費用を返す」だけの契約で、
作業状況は `onProgress`、危険な操作の承認は `requestApproval` でオーケストレータに戻す。

## セキュリティ

- ダッシュボードはトークン認証(HttpOnly Cookie または Bearer)。既定では `127.0.0.1` のみで待ち受ける。
- エージェントの出力は信頼できない内容として扱い、画面では必ずテキストとして表示する(`textContent`、CSP)。
- 成果物の閲覧はワークスペース内に限定する(パストラバーサル・シンボリックリンクを拒否)。

## 今後の拡張候補

- プロジェクトの一時停止・中止、タスク単位のやり直し

- 画像生成サービスとの連携(現在の designer は SVG または生成用の仕様を作る)
- SQLite などへの永続化の移行、複数ユーザーと権限
